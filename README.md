# 企微自建应用回调桥 v2.1

在企微自建应用里直接和 Marlowe 说话，查 NAS、管容器、管 ESXi VM，底部还有常驻菜单——
功能对齐 Telegram 3 号机器人（bot3 v2.3.1）的主菜单。

## 它是什么

v1.0 走的是**智能机器人长连接**：能回消息，但没有菜单。
v2.0 走的是**自建应用 + 回调 URL**：有菜单、能回卡片，但只读，危险操作一律回绝。
v2.1 在 v2.0 的基础上把功能做到和 TG 3 号一样全：

1. 底部菜单扩到 **3 个一级 × 每个 5 个子项**（总览 / 容器 / 更多），覆盖 TG 主菜单全部 16 项；
2. 每张模板卡片都带操作按钮（状态卡、容器管理卡、容器详情卡、ESXi 卡、告警卡、更新卡）；
3. 危险操作（启停/更新容器、清理镜像、VM 电源、重启 NAS、自我更新安装）改走**两步确认卡片**
   （✅ 确认 / ❌ 取消），确认 5 分钟过期，绝不在一次点击、一条文字命令里直接执行；
4. 新增主动告警（容器停了 / 磁盘满了 / 负载高 / 内存满了）、容器镜像更新检查（每 6 小时）、
   自我更新（检查 GitHub 新版本 → 确认 → 安装 → 重启容器）。

回调机制不变：企微把消息 POST 到跑在 NAS 上的这个服务，服务 5 秒内回 `success`
（慢活丢后台线程做），再用自建应用接口把答案主动发回给你。

为什么 v2 必须跑在 NAS 上：回调地址要公网可达、发消息要过可信 IP 检查。
Muse VM 的出口 IP 轮换，过不了可信 IP（60020）；NAS 在家里，出口 IP 就是家里宽带的
IP，手动加进可信 IP 列表就行，回调地址用你现有的 Lucky 反代域名暴露出去。

## 显示效果（先说清楚，避免踩坑）

- **状态 / 磁盘 / 温度一律发模板卡片**：主标题 + 横向 key-value 行 + 按钮行。
  状态卡按钮：温度详情 / 磁盘详情 / 容器列表 / 刷新 / 主菜单。
- **容器列表 / 容器资源 / 进程 TOP / 网络流量发 markdown 短行**：每容器/每进程/每网卡一行。
- **绝不发 emoji 彩条文本块**：🟥🟩 拼成的用量条在企微里会从色条中间换行、错位，
  朋友截图里就是这么难看的——v2 里已经彻底删掉这种渲染。

### 取舍（TG 模式在企微里放不下的地方）

- **卡片每张最多 6 个按钮**（官方限制）：TG 容器管理是每容器一个按钮，企微放不下，
  所以容器管理卡用**编号列表 + 回复序号选容器**（例如回 `3`），再进详情卡。
  详情卡 6 个操作按钮占满（启动/停止/重启/看日志/搜日志/更新容器），返回靠底部菜单。
- **ESXi VM 超过 5 个时**：列表卡按钮放不下，改走编号列表 + 回复序号选 VM（和容器管理一样）。
- **“给 Muse 下指令”跳转按钮**：TG 是 `t.me/MuseAI6_Bot` 的 URL 按钮；企微模板卡片的
  按钮只有 click（回传 key），没有跳外部链接的类型，所以省略。
  想给 Marlowe 下非服务器任务，直接在企微里发文字聊天就行（走 LLM）。
- **/docker 的启停命令**：TG 是直接执行；企微一律先出确认卡，点 ✅ 才执行。
  这是 ww 的规矩：只做授权过的操作，不在一次命令里直接改容器。
- **容器更新结果卡最多列 5 个待更新容器**（5 个 [更新] 按钮 + 1 个 [主菜单] = 6 个上限），
  超出的在卡片副标题里写“还有 N 个”，点“检查容器更新”重新查能看到全部。
- **重启 NAS 不进菜单**：TG 里也要点两次确认；企微这里只接受文字“重启 NAS”再出确认卡，
  绝不一键触发。

## 部署步骤（在 NAS 上操作，全新安装看这里）

⚠️ **先看顺序**：第 1 步新建应用 → 第 2 步拷文件填 `.env` → 第 3 步启动桥 →
**第 4 步再去后台保存回调地址**。回调地址保存时，企微会立刻发一个 GET 请求验证
echostr，桥没跑起来就验证失败、保存不上。所以回调配置必须是第 4 步，不能提前。

### 第 1 步：新建自建应用（电脑上操作）

> ⚠️ 旧的自建应用已经删了，旧的 AgentId 和 Secret 都已失效，
> 旧的企微 vault 凭证也作废了，**一律不要再用**。下面是新建流程。

1. 企业微信管理后台 → 应用管理 → 自建 → **创建应用**。
2. 填应用名称（例如 `Marlowe`）、上传一个 logo；
   **可见范围一定要选上你自己**（例如 WangDeWei），不然你收不到消息、也点不了菜单。
3. 建好后点进应用，记下 **AgentId** 和 **Secret**（Secret 点“查看”，按提示验证后显示）。
   这两个值只填进 NAS 上的 `.env`，**绝不要发到聊天里**。
4. 同一页面记下企业 ID（管理后台 → 我的企业 → 企业信息 → 企业 ID），也要填进 `.env`。

### 第 2 步：拷文件、填 `.env`

```bash
# 1. 把这 6 个文件拷到 NAS（和 bot3、v1 桥同一级目录）
#    wecom_callback.py  Dockerfile  docker-compose.yml  requirements.txt  .env.example  README.md
#    目标目录：/mnt/Strongge/docker-compose/wecom-callback/

cd /mnt/Strongge/docker-compose/wecom-callback

# 2. 建 .env，在 NAS 上直接填（Secret 绝不要经过聊天发过来）
cp .env.example .env
nano .env
#   WECOM_CORPID=    第 1 步记下的企业 ID
#   WECOM_SECRET=    第 1 步新建应用的 Secret（旧应用的已失效，别填错）
#   WECOM_AGENTID=   第 1 步新建应用的 AgentId
#   WECOM_TOKEN=     下面第 4 步里你自己定的回调 Token（和后台填的同一串）
#   WECOM_AESKEY=    下面第 4 步里后台“随机生成”的 EncodingAESKey（43 位）
#   OWNER_USERIDS=   你的企微 userid，例如 WangDeWei（多个用英文逗号隔开）
#   LLM_API_KEY=     聊天后端 Key（AnyRouter 的 Key）
#   ESXI_HOST=       （可选）ESXi 主机地址，填了才能用 ESXi VM、重启 NAS
#   ESXI_USER=       ESXi 用户名，一般 root
#   ESXI_PASSWORD=   ESXi 密码（或用 ESXI_KEY_FILE 走 key，见 .env.example）
#   NAS_VM_NAME=     NAS 这个 VM 在 ESXi 里的名字（或 NAS_VM_ID 填数字 ID）
#   UPDATE_REPO=     （可选）自我更新的 GitHub 仓库，例如 wdw6733/wecom-callback-bridge
```

### 第 3 步：启动桥

```bash
docker compose up -d --build

# 看日志，确认服务起来了
docker compose logs -f wecom-callback
# 应该看到：企微自建应用回调桥 v2.1.0 启动：监听 0.0.0.0:18789
```

### 第 4 步：在企微后台配回调地址（桥跑起来之后才能配）

1. 企业微信管理后台 → 应用管理 → 自建应用 → 点进**新建的**应用 →
   **接收消息 → 设置 API 接收**。
2. 填三项：
   - **URL**：`https://你的域名/wecom/callback`（域名怎么来见下面“回调地址怎么暴露”）
   - **Token**：自己定一串字符（例如 `MarloweWecom2026`），和 `.env` 里的 `WECOM_TOKEN` 一模一样
   - **EncodingAESKey**：点“随机生成”，把生成的 43 位字符抄进 `.env` 的 `WECOM_AESKEY`
3. 点保存。企微会立刻发一个 GET 请求验证 URL：服务验签、解密 echostr、原样返回，
   通过才算保存成功。**如果桥没启动，这一步一定失败**——先回第 3 步确认容器在跑，
   再回来保存。
   注意：改了 `.env` 里的 Token / AESKey 要 `docker compose up -d` 重启容器再生效。

#### 回调地址怎么暴露

服务本身只监听 `18789` 端口，需要一个公网能访问到的地址指到它。按你的现有条件：

- **推荐**：用已有的 Lucky 反代域名（例如 `https://xxx.66012943.xyz/wecom/callback`），
  在 Lucky 里加一条 HTTP 反代规则指到 NAS 上这个容器的 `18789` 端口。
  域名有 A 记录（IPv4）就能走通；如果域名只有 AAAA 记录（纯 IPv6），
  ⚠️ **未验证**：企微回调服务器能不能访问纯 IPv6 的地址，目前没有实测证据。
  保存回调时如果验证失败，先把这个当作头号嫌疑：给域名补一条 A 记录指向家里宽带 IPv4，
  或改走下面公网 IP 的方式再试。
- **备选（企业未认证时）**：`http://家里公网IP:18789/wecom/callback`，
  路由器上把 18789 端口转发到 NAS。是否接受纯 `http://IP:端口` 形式的回调地址，
  ⚠️ **未验证**：控制台保存时以实际校验结果为准，不行就改用域名 + HTTPS。

#### 企业认证和备案

- 企业微信**已认证**的企业：回调域名一般要求有 ICP 备案，且备案主体要和企微认证主体一致，
  否则保存回调时可能被拒。你的域名 `66012943.xyz` 是否已备案、备案主体是谁，
  **需要你自己确认**，这一步我没法代查。
- 企业**未认证**：可以用公网 IP + 端口做回调地址（见上面备选），不需要备案域名。

### 第 5 步：配可信 IP（否则发不出消息）

发消息（gettoken 之后调 message/send）会查企业可信 IP，出口 IP 不在列表里就报 `60020`。

1. 先查家里宽带现在的公网出口 IP（NAS 上 `curl ifconfig.me`，或路由器管理页看）。
2. 管理后台 → 应用管理 → 自建应用 → 点进**新建的**应用，找到**企业可信 IP**一栏，
   把这个 IP 加进去保存。
   注意：配可信 IP 之前必须先配好回调地址（上面第 4 步），否则那一栏可能不让改。
3. ⚠️ 家里宽带 IP 可能会变（运营商定期重拨就换）。IP 变了之后桥就发不出消息（60020），
   要重新去后台改。这是自建应用这条路的固有维护成本：如果 IP 经常变，
   考虑给家里宽带申请固定 IP，或改回 v1.0 的机器人长连接（那条路不用可信 IP）。

### 第 6 步：建底部菜单

菜单有两种建法，效果一样，选一个：

#### 方法 A：命令行（推荐，跟着桥一起跑）

```bash
cd /mnt/Strongge/docker-compose/wecom-callback
docker compose exec wecom-callback python wecom_callback.py create-menu
# 返回 {"errcode":0,"errmsg":"ok"} 就是建好了
```

菜单内容（代码里的 `build_menu_payload()`），3 个一级 × 每个 5 个子项：

| 一级 | 子菜单（点一下发什么） |
| --- | --- |
| 总览 | 系统状态 / 公网 IP / 磁盘空间 / 温度 / 帮助 |
| 容器 | 容器列表 / 容器管理 / 容器资源 / 检查容器更新 / 清理镜像 |
| 更多 | ESXi VM / 网络流量 / 进程 TOP / 告警 / 检查更新 |

（一级最多 3 个、子菜单最多 5 个、只允许一级子菜单，这是企微的硬限制；
一级名字 ≤16 字节、子项名字建议 ≤7 个汉字、菜单 key ≤128 字节。
`create-menu` 会先按这些限制校验一遍，不合规直接报错、一次 HTTP 都不发。）

#### 方法 B：管理后台点

应用管理 → 自建应用 → 点进**新建的**应用 → **自定义菜单**，按上面表格手动加，
类型都选 click（点击推事件），key 按 `MENU_STATUS`、`MENU_IP`、`MENU_DISK`、
`MENU_TEMP`、`MENU_HELP`、`MENU_CONTAINERS`、`MENU_MANAGE`、`MENU_STATS`、
`MENU_CHECK_UPDATES`、`MENU_PRUNE`、`MENU_ESXI`、`MENU_NET`、`MENU_TOP`、
`MENU_ALERTS`、`MENU_SELFUPDATE` 填。

菜单建好后，在企微里重新进一次应用就能看到底部菜单。点一下，桥会把结果发回来。
卡片里的按钮也一样：点了就发一张新卡片或新消息（危险操作先出确认卡）。

## 白名单 userid 怎么填

- 如果应用创建者是**企业超级管理员**，回调里的 userid 就是明文，直接填你的 userid
  （例如 `WangDeWei`）。
- 如果创建者**不是超级管理员**，回调里的 userid 可能是加密的：先把 `OWNER_USERIDS` 留空
  启动一次，给应用发一条消息，看日志里打印的 `收到的 userid 是：xxx`，
  把那个值填进 `.env` 的 `OWNER_USERIDS`，再 `docker compose up -d` 重启。

## 排障

| 现象 | 原因 / 做法 |
| --- | --- |
| 保存回调时提示“URL 验证失败 / echostr 校验失败” | 桥没跑（先回第 3 步确认容器在跑），或回调地址不可达，或 Token / EncodingAESKey 和 `.env` 里不一致。先看容器日志有没有“URL 验证通过”：有 = 地址通了，是 Token/AESKey 对不上；没有 = 企微根本没连进来，检查反代规则、端口转发、域名解析（尤其纯 IPv6 域名，见上面）。 |
| 日志 `回调消息签名不匹配` / `URL 验证签名不匹配` | Token 填错了（后台填的和 `.env` 里的 `WECOM_TOKEN` 必须一模一样）。 |
| 日志 `解密失败` / `PKCS7 填充校验失败` | EncodingAESKey 填错了（43 位，后台“随机生成”的那个，和 `.env` 里必须一致）。 |
| 发消息报 `60020` | 出口 IP 不在可信 IP 列表。按“第 5 步”加家里现在的公网 IP；IP 变了要重新加。 |
| 发消息报 `40001 / 41001` | Secret 无效或被换过。**先确认填的是新建应用的 Secret**——旧应用已删，旧 Secret 已失效，填旧的必报这个错。 |
| 发消息报 `40003 / 40004` | 接收人 userid 无效。核对 `OWNER_USERIDS` 填的是回调日志里打印的那个 userid，且该成员在应用可见范围里（第 1 步建应用时可见范围要包含你）。 |
| 用户发消息后企微重试、收到多条重复回复 | 服务 5 秒内没回 `success`（LLM/查 NAS 太慢被拖住了）。v2 的设计是 POST 里只排队、立即回 `success`，出现重试先看日志：是不是后台线程卡住了；另外检查容器是不是太忙。 |
| 发了消息没反应 | 先看日志：有没有“收到消息”？没有 = 回调没进来（看上面验证失败那行）；有但被拒绝 = 白名单没配好（看日志打印的 userid）。 |
| 菜单点了没反应 | 菜单的 key 是否是 15 个 `MENU_*` 之一；容器日志里有没有“菜单点击”；另外菜单改完要重新进一次应用才生效。 |
| 卡片按钮点了没反应 | 卡片按钮的 key 是 `CARD_*` / `MG_*` / `C_*` / `E_*` / `ALERT_*` / `U_ASK_*` / `CF_*`，容器日志里搜“卡片按钮点击”；没有 = 回调事件没进来（看上面验证失败那行）。 |
| 点了 ✅ 确认却回“这个确认已过期” | 确认卡只有 5 分钟有效；点 ❌ 取消、别人点、容器重启都会让它失效。重新操作一次。 |
| 点了“重启 NAS”/“ESXi VM”回“未配置” | `.env` 里没填 `ESXI_HOST`（和 `NAS_VM_NAME` 或 `NAS_VM_ID`）。填好后 `docker compose up -d` 重启。 |
| 点了“检查更新”回“自我更新未配置” | `.env` 里没填 `UPDATE_REPO`（例如 `wdw6733/wecom-callback-bridge`）。填好后重启。 |
| 容器管理里回复序号没反应 | 序号只在点开管理卡后的 10 分钟内有效；过期了重新点“容器管理”。 |
| 聊天回答“聊天功能还没配好” | `.env` 里没填 `LLM_API_KEY`。本地查询不受影响。 |
| 容器日志查不到 | 容器名不对（用“容器列表”看准确名字），或 docker.sock 没挂载好。 |
| 容器更新失败、提示“已回滚到旧容器” | 新容器没跑起来（看新容器日志排查镜像/配置问题），旧容器已恢复在跑，不用慌。 |
| 告警收不到 | 先确认告警开关是开的（点“告警”卡片看开关）；再确认阈值（磁盘 90%、负载核数×2、内存 92%）；同一种告警 1 小时内只发一次。 |

**v1 和 v2 不能同时用同一个身份**：v1 用的是智能机器人（Bot ID），v2 用的是自建应用
（AgentId），两者是不同的入口，可以并存；但同一个自建应用不要再配别的回调地址，
否则消息会被另一边收走。

## 协议依据

企业微信开发者中心《接收消息》（自建应用回调）：
https://developer.work.weixin.qq.com/document/path/90930

- 签名：sha1(sorted([token, timestamp, nonce, encrypt_msg]))
- 加解密：AES-256-CBC，16 字节随机 + 4 字节大端长度 + 消息 + corpid，PKCS7 补到 32 字节
- GET 验证 echostr；POST 信封解密；5 秒内回 `success`，否则重试 3 次
- message/send 文本上限 2048 字节；模板卡片 `template_card`（button_interaction，
  horizontal_content_list 最多 6 行，button_list 最多 6 个按钮，
  keyname 建议不超过 5 个字、value 建议不超过 30 个字，按钮点击回 template_card_event）；
  自定义菜单一级最多 3 个、子菜单最多 5 个、一级名字 ≤16 字节、菜单 key ≤128 字节
